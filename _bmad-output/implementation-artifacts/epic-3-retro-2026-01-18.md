### 3. API Integration Complexity Handled Systematically

**What Happened:**
We integrated 3 complex external APIs with different patterns:
1. **Gemini (Story 3-3):** Synchronous image generation, 20-40s per image, retry on timeout
2. **Kling via KIE.ai (Story 3-5):** Two-phase (upload → poll), 2-5 min per clip, catbox.moe hosting
3. **ElevenLabs (Stories 3-6, 3-7):** Streaming audio generation, 5-15s per clip, rate limiting

**Why It Worked:**
- **Async-First Design:** All API calls wrapped in `asyncio.to_thread()` to prevent event loop blocking
- **Short Transaction Pattern:** Database connections closed during API calls (2-5 minute Kling calls)
- **Timeout Strategy:** Per-API timeouts (60s Gemini, 600s Kling, 120s ElevenLabs)
- **Error Classification:** Transient errors (retry) vs permanent errors (fail immediately)
- **Rate Limit Awareness:** Batch processing with delays for ElevenLabs (3 req/sec limit)

**Example: Kling API Integration (Story 3-5)**
```python
# Challenge: Kling requires publicly-hosted images, takes 2-5 min per clip
async def generate_video_clip(composite_path, motion_prompt):
    # Step 1: Upload to catbox.moe (free public hosting)
    image_url = await upload_to_catbox(composite_path)

    # Step 2: Submit to Kling API (close DB connection first!)
    generation_id = await kling_client.submit_generation(image_url, motion_prompt)

    # Step 3: Poll for completion (2-5 min, exponential backoff)
    while True:
        status = await kling_client.check_status(generation_id)
        if status == "complete":
            return await kling_client.download_video(generation_id)
        if status == "failed":
            raise CLIScriptError("Kling generation failed")
        await asyncio.sleep(30)  # Poll every 30 seconds
```

**Quantitative Results:**
- **18 video clips** generated per pipeline (Kling)
- **22 asset images** generated per pipeline (Gemini)
- **36 audio clips** generated per pipeline (ElevenLabs: 18 narration + 18 SFX)
- **Total API calls per video:** 76 calls across 3 services
- **Success rate:** 100% in testing (no failed generations)
- **Cost accuracy:** Within 5% of estimated ($6-13 actual vs $6-12 estimated)

**Team Impact:**
- Charlie: "The hardest part was the catbox.moe requirement for Kling. Once we figured out the two-phase upload → generate pattern, it was smooth."
- Alice: "The short transaction pattern was non-negotiable. Holding DB connections during 5-minute Kling calls would have been catastrophic."

### 2. Catbox.moe Single Point of Failure 🟡

**What Happened:**
Kling API requires publicly-accessible image URLs. We chose catbox.moe (free anonymous hosting) for MVP, but it's a single point of failure with no SLA.

**Impact:**
- **Reliability Risk:** If catbox.moe is down, video generation fails entirely
- **No Retry Logic:** Current implementation fails immediately if upload fails
- **No Monitoring:** We don't track catbox.moe availability or latency

**Why We Chose catbox.moe:**
- Free (no cost for MVP)
- No authentication required (simple integration)
- Fast upload times (1-3 seconds per image)
- Worked reliably during testing (100% uptime observed)

**What We Should Have Done:**
1. **Fallback Strategy:** Support multiple hosting providers (catbox.moe → imgbb.com → Cloudflare R2)
2. **Retry Logic:** Exponential backoff for transient upload failures
3. **Monitoring:** Track upload success rate, alert if drops below 95%

**Why This Persisted:**
Story 3.5 (Video Generation) focused on Kling API integration. Catbox hosting was implemented as the simplest path to unblock testing. The team decided to defer hosting reliability to Epic 8 (Monitoring & Observability).

**Team Discussion:**
- **Dana:** "We got lucky that catbox.moe was stable during testing. One outage and the entire system stops."
- **Alice:** "This is a classic 'MVP vs production-ready' trade-off. For Epic 3, catbox was good enough. For Epic 8, we need redundancy."
- **Elena:** "Cloudflare R2 is $0.015/GB storage. Even at 100 videos/day (18 composites × 2 MB each), that's $1/month. Worth the reliability."

### 3. Test Fixtures Didn't Match Production Edge Cases 🟡

**What Happened:**
Despite 265 tests, code review caught 12 critical bugs that tests missed. Most were edge cases where test fixtures used simplified data (e.g., tests assumed `video_url` was always set, production reality was it could be None).

**Evidence from Story 3.9 Code Review:**

**Bug #1: Task.video_url Never Updated**
```python
# Test fixture (simplified)
task = create_task(video_url="https://example.com/video.mp4")  # Always present

# Production reality
task = create_task()  # video_url=None until assembly completes!

# Test passed because fixture always had video_url
# Code review caught: "Where do you set task.video_url?"
```

**Bug #2: Missing Error Status Mapping**
```python
# Test assumed all steps had error mappings
step = PipelineStep.COMPOSITE_CREATION

# Test passed because it only tested steps that HAD error mappings
# Code review caught: "What if COMPOSITE_CREATION fails?"
```

**Why Tests Missed These:**
1. **Optimistic Fixtures:** Test data represented "success case" not "real world"
2. **Limited Edge Cases:** Tests covered happy path and obvious failures, not subtle bugs
3. **Mock Realism Gap:** Mocked services returned perfect data (no None, no unexpected formats)

**What We Should Have Done:**
1. **Adversarial Test Design:** Write tests assuming worst-case inputs (None, empty strings, malformed JSON)
2. **Production Data Sampling:** Copy real database records into test fixtures (anonymized)
3. **Fuzzing:** Generate random inputs to catch validation gaps

**Why This Persisted:**
- **Test-First Development:** Tests written before implementation led to "test what you built" not "test what could break"
- **Time Pressure:** Epic 3 had aggressive 2-day timeline, edge case testing deprioritized
- **Code Review Safety Net:** Team relied on adversarial review to catch gaps (which it did)

**Team Discussion:**
- **Dana:** "I'm frustrated we didn't catch these in tests. The fixtures were too clean - real production data is messy."
- **Charlie:** "Code review saved us, but that's reactive. We need proactive edge case testing."
- **Alice:** "This is a known pattern: tests validate the implementation, code review validates the requirements. Both are necessary."

## Key Insights & Learnings

### 1. "Smart Agent + Dumb Scripts" Architecture Scales ⭐⭐⭐

**Insight:**
The architectural pattern established in the Pokemon pipeline (agents orchestrate, scripts execute) translated perfectly to the multi-channel orchestration platform. All 8 pipeline steps followed this pattern with zero architectural friction.

**Pattern Definition:**
```
Smart Agent (Orchestrator):
- Reads project files and database
- Extracts data and combines prompts
- Handles errors and retries
- Manages state and transitions
- Orchestrates workflow

Dumb Script (CLI Tool):
- Takes complete inputs via arguments
- Calls one API
- Returns success/failure via exit code
- No file reading, no business logic
- Stateless and testable
```

**Evidence from Stories:**

**Story 3.1:** CLI wrapper established `asyncio.to_thread()` pattern for all subprocess calls
```python
# Orchestrator (smart)
result = await run_cli_script(
    "generate_asset.py",
    args=["--prompt", combined_prompt, "--output", output_path],
    timeout=60
)

# Script (dumb)
# scripts/generate_asset.py receives complete prompt, generates image, exits
```

**Story 3.3:** Asset generation service combined manifest + global atmosphere, script just called API
```python
# Service (smart - combines prompts)
combined_prompt = f"{manifest.global_atmosphere}\n\n{asset.description}"
result = await run_cli_script("generate_asset.py", ["--prompt", combined_prompt])

# Script (dumb - just calls Gemini API, no file reading)
```

**Why This Worked:**
- **Clear Separation:** No ambiguity about where logic belongs
- **Testability:** Services tested with mocked subprocess calls, scripts tested standalone
- **Brownfield Constraint:** Scripts are legacy Pokemon pipeline code, untouchable
- **Error Handling:** Orchestrator handles transient vs permanent errors, scripts just fail

**Team Impact:**
- **Alice:** "This pattern is brilliant. The scripts are pure functions (input → API call → output), which makes them dead simple to reason about."
- **Charlie:** "I never had to decide 'should the script do this or the service?' The boundary was crystal clear."

**Lessons for Future Epics:**
- Continue this pattern in Epic 4 (Worker Orchestration) - workers are orchestrators, services are smart agents
- Never add business logic to CLI scripts - if logic is needed, add it to the service layer
- Consider extracting this pattern into project-context.md as a mandatory architectural rule

### 4. External API Integration Requires Defensive Programming

**Insight:**
All 3 external APIs (Gemini, Kling, ElevenLabs) had undocumented behaviors discovered during testing:
1. **Gemini:** Occasionally times out after 40s (not 20s as documented)
2. **Kling:** Rate limits not clearly documented (discovered through trial and error)
3. **ElevenLabs:** Streaming responses sometimes stall mid-stream

**Defensive Patterns Implemented:**

**1. Extended Timeouts Beyond Documented Limits:**
```python
# Gemini docs say "20-30s typical"
GEMINI_TIMEOUT = 60  # 2x buffer for safety

# Kling docs say "2-5 min typical"
KLING_TIMEOUT = 600  # 10 min absolute maximum (observed max: 8 min)

# ElevenLabs docs say "5-10s typical"
ELEVENLABS_TIMEOUT = 120  # 2x buffer for streaming stalls
```

**2. Output Validation Before Marking Complete:**
```python
# Don't trust API "success" response - verify output
async def generate_video_clip(composite, prompt):
    video_path = await kling_client.generate(composite, prompt)

    # Verify file exists
    if not video_path.exists():
        raise CLIScriptError("Kling returned success but file missing")

    # Verify file is valid video (ffprobe)
    duration = await probe_video_duration(video_path)
    if duration < 5.0:
        raise CLIScriptError(f"Video too short: {duration}s (expected 10s)")

    return video_path
```

**3. Rate Limit Backoff (Learned Through Trial and Error):**
```python
# ElevenLabs docs don't mention rate limits clearly
# Discovered through testing: 3 req/sec limit, 429 errors after burst

ELEVENLABS_RATE_LIMIT = 3  # requests per second
ELEVENLABS_BACKOFF_SECONDS = 5  # wait after 429 error

async def generate_narration_batch(clips):
    for i, clip in enumerate(clips):
        await generate_narration(clip)
        if (i + 1) % ELEVENLABS_RATE_LIMIT == 0:
            await asyncio.sleep(1)  # Throttle to stay under limit
```

**4. Retry Logic for Transient Failures:**
```python
async def call_api_with_retry(api_call, max_retries=3):
    for attempt in range(max_retries):
        try:
            return await api_call()
        except (TimeoutError, ConnectionError) as e:
            if attempt < max_retries - 1:
                backoff = 2 ** attempt  # Exponential: 1s, 2s, 4s
                log.warning(f"API call failed, retrying in {backoff}s", error=str(e))
                await asyncio.sleep(backoff)
            else:
                raise  # Final attempt failed
```

**APIs are Unpredictable - Expect the Unexpected:**
- **Documented behavior ≠ actual behavior:** Always add safety margins
- **Validate outputs:** Don't trust API "success" responses
- **Monitor error patterns:** APIs change behavior without notice (rate limits, timeouts)
- **Build observability:** Log API latencies, error rates, retry counts

**Lessons for Future Epics:**
- **Epic 7 (YouTube API):** Expect undocumented rate limits, add 2x timeout buffers
- **Epic 8 (Monitoring):** Track API error rates to detect behavior changes
- **Epic 6 (Error Handling):** Classify errors per-API (Kling timeout vs Gemini timeout have different retry strategies)

### 1. Kling API Motion Prompt Priority Hierarchy ⭐

**Discovery:**
Kling AI prioritizes the **beginning of motion prompts** over the end. Camera movements at the start override scene actions at the end.

**What We Tried (Wrong):**
```
# ❌ Camera movement first (Kling prioritizes this)
"Slow zoom in on Haunter. Haunter floats in dark corridor. Haunter presses both clawed hands against wall attempting to phase through. Haunter bounces backward unable to phase. Purple glow pulses brighter."

# Result: Kling focused on "slow zoom in" and ignored the wall-phasing action
```

**What Worked (Right):**
```
# ✅ Core action first, camera last (Kling prioritizes this)
"Haunter floats in dark corridor. Haunter presses both clawed hands against wall attempting to phase through. Haunter bounces backward unable to phase. Purple glow pulses brighter. Slow zoom in."

# Result: Kling animated the wall-phasing action correctly, then added zoom
```

**Priority Hierarchy (Discovered Through Testing):**
1. **Core Action FIRST** - What is happening (Haunter presses hands on wall)
2. **Specific Details** - What parts move, how they move (both clawed hands)
3. **Logical Sequence** - Step-by-step cause and effect (presses → bounces → glow)
4. **Environmental Context** - Atmosphere, lighting, weather (dark corridor, purple glow)
5. **Camera Movement LAST** - Aesthetic enhancement only (slow zoom in)

**Impact:**
- **Quality:** Videos matched story intent (not just camera movements)
- **Iteration:** Reduced video re-generation from 3-4 attempts to 1-2 attempts per clip
- **Cost Savings:** ~$2-4 saved per video (fewer Kling regenerations)

**Documentation:**
Added to `CLAUDE.md` (lines 42-56) as mandatory pattern for all future video generation.

**Team Impact:**
- **Charlie:** "This took a full day to figure out. Kling's docs don't mention prompt structure at all."

### 2. Short Transaction Pattern Scales to 2-Hour Operations ⭐⭐

**Discovery:**
PostgreSQL connections can safely be closed for 2-hour operations (Kling video generation) without data loss or state corruption. The "claim → close → process → reopen → update" pattern worked flawlessly.

**Pattern Validation:**

**Story 3.9 Implementation:**
```python
# Step 1: Claim task (short transaction, 50ms)
async with AsyncSessionLocal() as db:
    async with db.begin():
        task = await db.get(Task, task_id)
        task.status = TaskStatus.PROCESSING
        await db.commit()

# Connection closed here - CRITICAL!

# Step 2: Execute pipeline (51-124 minutes, NO DB HELD)
orchestrator = PipelineOrchestrator(task_id)
await orchestrator.execute_pipeline()

# Step 3: Reopen connection, update status (short transaction, 50ms)
async with AsyncSessionLocal() as db:
    async with db.begin():
        task = await db.get(Task, task_id)
        task.status = TaskStatus.FINAL_REVIEW
        task.pipeline_duration_seconds = duration
        await db.commit()
```

**What We Validated:**
1. **No Data Loss:** Task state persisted correctly across 2-hour gap
2. **No Race Conditions:** Concurrent workers didn't conflict (row-level locking)
3. **Worker Crash Recovery:** If worker crashes, task is auto-released after 10 minutes
4. **Connection Pool Health:** No connection pool exhaustion (3 workers, 2-hour operations)

**Performance Metrics:**
- Transaction time: ~50ms (claim) + ~50ms (update) = 100ms total
- Processing time: 51-124 minutes (outside transaction)
- Connection pool: 3 workers × 2 connections each = 6 connections max (PostgreSQL default: 100)
- Zero connection pool exhaustion incidents

**Why This Matters:**
- **Scalability:** Can run 10+ workers concurrently without connection pool issues
- **Reliability:** Worker crashes don't leave database in locked state
- **Performance:** PostgreSQL connection pool remains healthy under load

**Lessons for Future Epics:**
- **Epic 4 (Worker Orchestration):** Continue short transaction pattern for all workers
- **Epic 7 (YouTube Upload):** Apply same pattern for resumable uploads (10-60 min operations)
- **Architectural Rule:** Extract to architecture.md as mandatory pattern for long operations

**Team Impact:**
- **Alice:** "I was skeptical this would work for 2-hour operations. The validation proves it's rock-solid."
- **Charlie:** "The pattern is simple once you internalize it: claim, close, work, reopen, update. No holding connections."

### 3. Notion Status Sync Must Be Fire-and-Forget ⭐

**Discovery:**
Synchronous Notion API calls (3-5 seconds each) added 30-45 seconds to pipeline duration (6 status updates × 5 seconds). Making Notion sync async (fire-and-forget) eliminated blocking.

**Before (Synchronous Notion Updates):**
```python
async def update_task_status(task_id, status):
    # Update database (50ms)
    async with db.begin():
        task.status = status
        await db.commit()

    # Update Notion (3-5 seconds - BLOCKS PIPELINE!)
    await notion_client.update_status(task.notion_page_id, status)
    # Pipeline waits here for 3-5 seconds before continuing
```

**After (Asynchronous Fire-and-Forget):**
```python
async def update_task_status(task_id, status):
    # Update database (50ms)
    async with db.begin():
        task.status = status
        await db.commit()

    # Update Notion (fire-and-forget - NON-BLOCKING!)
    asyncio.create_task(self._sync_to_notion_async(status))
    # Pipeline continues immediately, Notion updates in background
```

**Performance Impact:**
| Scenario | Sync Time | Async Time | Savings |
|----------|-----------|------------|---------|
| Single status update | 3-5 sec | ~50ms | 2.95-4.95 sec |
| Full pipeline (6 updates) | 18-30 sec | ~300ms | 17.7-29.7 sec |
| 100 videos/day | 30-50 min | ~30 sec | 29.5-49.5 min |

**Why Fire-and-Forget is Safe:**
1. **Database is Source of Truth:** If Notion update fails, database still correct
2. **Eventual Consistency:** Notion updates within 5 seconds (acceptable for user visibility)
3. **Retry Logic:** Failed Notion updates are retried in background
4. **Non-Critical:** Notion is for user visibility, not system state

**Implementation Details:**
```python
async def _sync_to_notion_async(self, status: TaskStatus) -> None:
    try:
        # Load task data (short transaction)
        async with AsyncSessionLocal() as db:
            task = await db.get(Task, self.task_id)
            notion_page_id = task.notion_page_id

        # Close DB, call Notion API (slow)
        await notion_client.update_status(notion_page_id, status)

    except Exception as e:
        # Log error but don't fail pipeline
        self.log.error("notion_sync_failed", error=str(e))
```

**Lessons for Future Epics:**
- **Epic 5 (Review Gates):** Apply same pattern for Notion review status updates
- **Epic 7 (YouTube Upload):** Apply same pattern for YouTube URL updates
- **Architectural Rule:** All external notifications (Notion, Slack, email) should be fire-and-forget

**Team Impact:**
- **Elena:** "Users won't notice the 5-second delay. They care more about the pipeline not taking 3 hours."
- **Charlie:** "Fire-and-forget is scary at first, but the database is the source of truth. Notion is just a mirror."

### 4. FFmpeg Composite Creation is Instant (1-2 minutes for 18 composites) ⭐

**Discovery:**
Creating 18 × 1920x1080 composites from character + environment images takes only 1-2 minutes using FFmpeg, making it a negligible bottleneck.

**Performance Breakdown:**

Single Composite Creation:

- Load environment JPG (1920x1080): ~15ms
- FFmpeg composite operation: ~50-100ms
- Save output PNG (1920x1080): ~20ms
Total per composite: ~95-145ms

18 Composites Total: 1.7-2.6 seconds

Why 1-2 minutes observed?
- Sequential processing (not parallelized)
- Disk I/O overhead (20-40ms per file)
- Database status updates (3-5 updates × 50ms)
Actual measured time: 60-120 seconds

**Why This Matters:**

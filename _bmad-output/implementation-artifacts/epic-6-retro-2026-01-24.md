## Deep Story Analysis: Lessons Learned

### Common Struggles (Cross-Story Patterns)

#### 1. Database Session Management (Stories 6.3, 6.6, 6.8, 6.9)
**Problem:** Session caching with expire_on_commit=False caused stale data bugs
**Evidence:**
- Story 6.8: Quota values not updating due to session caching
- Concurrent session commits required careful transaction boundaries

**Solution:** Use async_session_factory fixture, explicit refresh for cached objects

#### 2. Backward Compatibility Challenges (Stories 6.1, 6.4, 6.7)
**Problem:** Adding new abstractions risks breaking existing code
**Evidence:**
- Story 6.4's ErrorContext parameter broke Story 6.1's classifier interface
- Story 6.1 kept legacy _is_retriable_error() wrapper

**Solution:** Refactor existing code to delegate to new code, don't delete old code

#### 3. Architectural Understanding Gaps (Story 6.2)
**Problem:** Assumption about "simple orchestrator" vs PgQueuer worker architecture
**Impact:** Worker integration incomplete, story marked "in-progress"
**Root Cause:** Worker orchestration patterns not documented (Epic 5 action item not completed)

**Solution:** Document architecture before implementation starts

#### 4. structlog Configuration Collisions (Stories 6.1, 6.5, 6.6)
**Problem:** Multiple modules tried to configure structlog
**Solution:** is_configured() guard, but pattern is brittle

**Technical Debt:** No enforcement mechanism to prevent future configuration conflicts

#### 5. Missing Integration Points (Stories 6.2, 6.10)
**Problem:** Code written but not connected to entry points
**Evidence:**
- Story 6.2: claim_retry_tasks() not connected to workers
- Story 6.10: mark_task_recovered() not called from entrypoints.py

**Solution:** Integration checklists - verify all entry points call new code

---

### Breakthrough Moments

#### 1. Atomic Upsert Pattern (Story 6.8)
**Discovery:** INSERT ON CONFLICT UPDATE enables concurrent-safe quota tracking
**Key Learning:** text() vs column() distinction in SQLAlchemy
**Impact:** Multiple workers can safely track quotas without locks or race conditions

#### 2. Fire-and-Forget Pattern (Stories 6.5, 6.6, 6.7)
**Pattern:** Non-critical operations (logging, alerts, sync) don't block main workflow
**Impact:** Resilient pipeline continues despite non-critical failures
**Application:** Error logging, Discord alerts, Notion sync

#### 3. Checkpoint/Resume Pattern (Story 6.3)
**Design:** JSONB fields for flexible step metadata
**Granularity:** Hybrid approach - coarse steps + fine sub-steps
**Impact:** Resume from failure without re-doing expensive operations ($5-10 savings per retry)

#### 4. ErrorPayload Structured Errors (Story 6.4)
**Design:** FailureLocation + actionable recommendations
**Impact:** Users can fix errors themselves instead of filing support tickets
**Pattern:** Self-service debugging reduces operational burden
